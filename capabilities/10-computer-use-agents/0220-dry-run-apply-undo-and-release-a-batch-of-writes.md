| Dry-run, apply, undo and release a batch of writes to external systems: `openadapt plan create/approve/apply/undo/release/cancel` over an `openadapt.tx.yaml` of REST collections, SQL tables and mail. The diff comes from a staged transaction (SQL), a computed shadow with declared server-set and derived fields (REST) or the holdback queue (email). Approval is single-use and bound to the plan digest, a stale plan is refused, each write's idempotency key comes from the task and the record slot (never the payload), and a retry with a different payload is refused (the ACRFence action-replay attack). The undo is verified by reading back each record and the whole frame. Irreversible writes wait in a cancelable holdback queue. A REST `replace` update or delete is `VERIFIED` only on a route whose `precondition` (`If-Match`) has enforcement evidence: a recorded probe, or a probe the adapter runs once per route. Without it the write is at best `COMPLETED_UNVERIFIED`, since another caller's edit after the plan read could be erased unseen. A REST undo sends the version it checked, and an undo without an enforced precondition ends `COMPLETED_UNVERIFIED`, never `ROLLED_BACK`. A SQL write whose rows change outside the current schema is refused, PostgreSQL deferred constraint triggers included. A SQL write is `VERIFIED` only when the catalog shows nothing that could write outside the frame; no function body is read to decide that. On PostgreSQL: no user-defined object (oid 16384 or more, any namespace) reachable through `pg_depend` from the frame relations, no user column type, no user function or SQL-running built-in in the planned statement as `EXPLAIN (VERBOSE)` resolves it, no planned DDL, and no event trigger, user cast or operator, foreign table, `dblink` or `postgres_fdw` in the database. On MySQL: database-level `SELECT` and `TRIGGER` grants, and no routines. Any trigger on a frame relation (MySQL: in the database) caps the write. The inventory is read before and after the write in its transaction, and a change between the two to the triggers, rules, casts, event triggers or column types that decide what the write runs caps it. An open item caps the write at `COMPLETED_UNVERIFIED` with a `not_covered` code; it doesn't refuse it. Replays and adoptions keep these caps.
