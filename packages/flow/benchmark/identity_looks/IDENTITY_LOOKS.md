# Extra identity looks on the dense record list: before and after

Generated by `benchmark/identity_looks/compare.py` from `results_before.json` (commit `426d08f2d`, origin/main) and `results_after.json` (commit `283336358`). Synthetic data only.

## What was measured

- The real `Replayer._verify_identity` against the dense record list of `benchmark/dense_surface` (40 rows, seeds 1, 2, 3), rendered live in Chromium and read by RapidOCR (`python -m openadapt_flow.validation.identity_looks_dense`).
- The pixel path the compiler builds for a pixel recording: the identifier region is the tight box around the row's identity text, and the recorded identity is the OCR text inside it.
- Replay conditions: hi_res_arial, native_arial, small_dense, serif_drift; each recorded at the same device scale as its replay. Click configs: click_name, click_action.
- A false stop is a click on the correct row that the check does not verify, at the step-entry check or at the check just before the click. A wrong-record accept is a click on the adjacent sibling row that verifies at either check. Both counts use the same 288 armed clicks.
- **Recorded record**: the band names the record the demonstration opened. **Run parameter**: the record's ID is a run parameter, as in a worklist, and the band embeds it.
- **Known-ID list**: every ID in the seed's table, as a complete list. **Copy look**: a real mouse drag across the identifier's text box in the live page; the copied text is the page's selection, which is what a redirected remote clipboard receives.
- The before run is origin/main, where the copy look does not exist. Its list column is the earlier design (one fresh capture).

## Headline

- No list, no copy: **232 / 288** correct-row clicks stop (no change; the extra looks need a list or a copy to settle anything).
- Known-ID list: **122 / 288** before, **122 / 288** after.
- Copy look with the ID as a run parameter: **24 / 288**; with the list too: **24 / 288**.
- Copy look in recorded-record mode: **232 / 288** (it can stop a run but never confirm one there).
- Wrong-record accepts: **0** across all 8 after configurations, and **0** before.

## What is left

Of the stops left with the copy look and a run parameter, almost all are in `id_confusion_O0` (IDs like `C0X1234`). There the recording itself read the ID with a letter O, so the recorded band does not contain the parameter's value and is not linked to it; with no exact value to compare, the copy can only agree, not confirm. The rest are dense-row reads that drop or garble a cell, a mismatch that no look may overrule. Per-trial looks are in `results_after.json`.

Without a run parameter (a workflow that always opens the recorded record), the copy confirms nothing: the recorded ID is OCR text and may itself be a misread. There, only the known-ID list helps.

## Limits

- One fixture, one OCR engine (RapidOCR), synthetic rows, a browser page. A real RDP or Citrix session adds compression and its own clipboard policy; many deployments turn clipboard redirection off, and then the copy look is unavailable.
- The fixture renders deterministically, so fresh frames repeat the first. These numbers show what the looks cost and settle, not what the fresh frames guard against (a caret or a repaint between captures).
- Selecting text in this table changes nothing. In an application where a drag on the identifier triggers something, the look stops the run if the screen changes outside the identifier, but the deployment must only turn the copy look on where selection is inert.
